How I turned a weird response header into 500 euros

The highest-paying bug I have found so far was not an RCE. It was not some elegant deserialization chain I spent a week nursing. It was a response header that looked wrong, on a subdomain I almost skipped.

500 euros. For noticing something weird and asking one more question instead of scrolling past it.

That is genuinely the whole story. If you take one thing from this post, take this: most bounties are not genius. They are curiosity backed by a repeatable method. Here is the method, step by step, exactly as it happened in March 2026.

Picking the target

I hunt on YesWeHack (handle MIHX01, if you want to say hi). That week I was in a recon mood and did not feel like staring at a single login page for six hours, so I wanted a target with a wide scope.

I picked a European SaaS company with *.company.com in scope. Wide scope means subdomains. Subdomains mean forgotten infrastructure. Forgotten infrastructure means debug pages, staging panels, and headers nobody reviewed since 2021. That is where information disclosure bugs live.

Rule one of my hunting: never start by hacking the main app. Start by mapping everything the company owns, then hack the parts they forgot about. The main app has been tested by every hunter on the platform. The forgotten API subdomain from a 2022 migration has been tested by nobody.

The recon that surfaced it

My subdomain pass is boring, and that is the point. Boring finds bugs.

bash
subfinder -d company.com -silent -o subs.txt

I also pull certificate transparency logs, because subfinder misses things and crt.sh is free:

bash
curl -s &quot;https://crt.sh/?q=%25.company.com&amp;output=json&quot; \
  | jq -r '.[].name_value' | sort -u &gt;&gt; subs.txt
sort -u subs.txt -o subs.txt
wc -l subs.txt

Then I check what is actually alive and fingerprint the tech stack in one pass:

bash
cat subs.txt | httpx -silent -title -status-code -tech-detect -o alive.txt

About 400 subdomains, around 90 alive. Most of them were the usual: marketing site, docs, status page, the main app, a helpdesk. I was about to start content discovery on the main app when one line in alive.txt caught my eye:

https://api.company.com [200] [API]

An API subdomain returning 200 on the root with no authentication. That is not automatically a bug. But open API roots are worth two minutes of poking, so I poked. Two minutes is my rule for anomalies: cheap to check, expensive to ignore.

The header that looked wrong

bash
curl -sI https://api.company.com/

Most of the headers were normal. CDN headers, content type, cache controls, the usual set. Then this:

X-Powered-By: Werkzeug/2.3.7 Python/3.11

Now, X-Powered-By leaking the exact framework and Python version is a small finding on its own. On most programs it gets closed as informative and you get zero euros and a polite email. I almost moved on.

But exact version numbers on an internet-facing API make me curious, for one specific reason: they tell me what the error pages look like. Frameworks running in debug mode produce beautiful, verbose, extremely talkative error pages. And a team that ships X-Powered-By with full versions to production is exactly the kind of team that might have left debug mode on somewhere.

So I asked the API a rude question. I requested a path that did not exist:

bash
curl -s https://api.company.com/this-path-does-not-exist-12345 | head -c 2000

And the API answered with a full HTML debug page. Traceback, local variables, everything.

That was the moment the 500 euros walked in. The header was the sign on the door. The debug page was the open vault behind it.

Confirming the leak

Before touching anything else, I confirmed what I had, cleanly and without authentication. This part matters, because a sloppy confirmation can turn into you accidentally testing something out of scope or tripping an alert. My checklist:

  1. 01Fresh session, no cookies, plain curl. The debug page rendered for anyone on the internet. No login, no token, no tricks.
  2. 02It triggered on any invalid path, not just one endpoint. I tried three different nonsense paths. All three gave the full traceback. The whole subdomain was in debug mode, not just one route.
  3. 03I catalogued exactly what leaked. Full Python tracebacks with absolute file paths (/opt/app/...), every installed package with exact versions, internal hostnames and IP addresses of backend services, and configuration fragments including service names I had no business knowing.
  4. 04I checked the disclosed versions for known CVEs without firing a single exploit. Two of the packages had public medium-severity CVEs. That strengthened my impact section enormously, and I never had to attack anything to get it. Proving impact is good. Actually exploiting the customer's API to prove impact is how you get banned from platforms.

Screenshot everything. Save the raw curl output to a file. Note the exact time and the exact request. Future you, writing the report at 2am, will thank present you. My evidence folder for this one was literally three files: the curl output, a screenshot of the traceback, and a text file with the list of leaked internals. That was enough for 500 euros.

Writing the report that got paid

My reports follow the same skeleton every time, because triage people are busy and a predictable structure gets accepted faster. This is not a theory, it is pattern recognition from my own accepted and rejected reports.

Title: Verbose debug mode enabled on api.company.com exposes internal infrastructure details

Boring title. Good. Titles are for triage search, not for impressing anyone.

Summary: two or three sentences. What is exposed, where, and the fact that it requires no authentication. If the triage analyst only reads the summary, they should still understand the bug.

Steps to reproduce: numbered and copy-pasteable.

1. Send a GET request to https://api.company.com/&lt;any-nonexistent-path&gt;
   (no authentication required):
   curl -s https://api.company.com/this-path-does-not-exist-12345
2. Observe the HTML response: a full framework debug page including
   Python tracebacks, absolute file paths, installed package versions,
   and internal hostnames/IP addresses.
3. Repeat with any other invalid path to confirm the entire subdomain
   runs in debug mode.

Thirty seconds to reproduce. Make their job easy and your reports get accepted faster.

Impact: I kept it honest and concrete. Internal IP addresses and hostnames hand an attacker a map of the internal network. Exact package versions let an attacker pick exploits off the shelf instead of guessing, and I named the two packages with public CVEs. File paths reveal the deployment layout. None of this is RCE by itself, but it deletes several steps an attacker would otherwise have to take. I said exactly that, in plain words. No fear-mongering, no "a nation-state actor could". Just the facts.

Remediation: disable debug mode in production (one config flag), serve a generic error page, strip version-disclosing headers. Three lines. Developers love three lines.

Severity: I suggested Medium with a CVSS vector. Triage agreed: Medium, CVSS 4.4.

Timeline: reported in the evening, triaged within a few days, bounty awarded: 500 euros. Plus 23 reputation points on the profile. My first big payout. The "NO BUGS LEFT BEHIND" t-shirt arrived later, and yes, I wear it.

Why information disclosure is underrated

Beginners ignore info disclosure because it does not feel like hacking. No shell pops. No dramatic redirect. Just... data sitting there.

But think about it from the attacker's side. Every serious attack chain starts with reconnaissance. When the application hands you its internal map for free, you did not just find a medium bug, you removed the hardest part of someone else's attack. That is why programs pay for it. The 500 euros was not for a header. It was for the three attack steps the header's debug page eliminated.

What I would do again (and what I would skip)

Do again:

  • Diff headers across subdomains automatically. I now run httpx with JSON output and use jq to list every unique header name per host. Anything custom gets a look. Custom headers are where developers confess things.
  • Trigger errors on every new subdomain. 404s, 500s, weird HTTP methods, overlong paths. Error handling is where applications talk too much. My standard probe set is: nonexistent path, path with %2e%2e, a POST to a GET endpoint, and a request with a garbage Content-Type.
  • Grep response bodies for debug smells. Traceback, stack trace, .py, node_modules, C:\, at Object. in JS. Debug pages have a smell and you can automate smelling it. I have a one-liner that flags any response containing these strings across my whole httpx output.

Skip:

  • Do not over-exploit to prove impact. For information disclosure, the disclosure IS the impact. Screenshots and curl output are enough. The moment you start poking the internal hosts you found, you have left "curious researcher" and entered "incident response trigger".
  • Do not write a five-page report for a one-command bug. Match the report size to the bug size. My report for this one was under a page.
  • Do not dismiss small weirdness. The header alone was worth nothing. The header plus one curious curl was worth 500 euros. The difference between those two outcomes was about forty seconds of curiosity.

That is the whole methodology. Map the scope, notice what looks wrong, confirm it cleanly, report it well. No genius required. Just curiosity, repeated daily, until the internet pays you for it.
